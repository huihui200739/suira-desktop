2. 一条后台监控路径确实使用 Dispatch timer

0x1001de648，204-monitor-start.pseudo.c:71–90：仅当 ClipboardHistoryService.timer == nil 时创建 DispatchSource timer，并使用 pasteboardQueue。

:93–104 的调用组合为 DispatchTime.now、时间加法常量 1.3、milliseconds(250)，再 schedule(deadline, repeating:1.3, leeway:...)。:109–144 将初始 lastChangeCount 放入捕获盒，安装闭包 0x10022eedc，使用弱引用盒，随后 resume 并保存 timer。

数值由同一 Evidence 的 204-monitor-start.assembly.json 复核：

  • 0x1001de8c0–0x1001de8cc 组装 0x3ff4cccccccccccd 并移入 d8，按 IEEE-754 double 解码为 1.3。
  • 0x1001de8d8 将 d8 作为 d0 传给 deadline 时间加法调用。
  • 0x1001de8f4–0x1001de918 构造数值 0xfa（250）和 DispatchTimeInterval.milliseconds 枚举。
  • 0x1001de920–0x1001de92c 再传 d8 给 timer schedule 导入函数 0x1018a6ea8。
  • 该 Evidence 的 callers 列表只给出直接调用者 0x1002b427c，函数体范围至 0x1002b42f7。本子任务没有继续反编译该调用者，其对应的产品生命周期状态由主线程的 runtime 研究补充。

证据：ev_6c676619d7c80efd243db29881ffa185ee91d14995c6b29b647045e29fd9ba6a。

范围限制：这是这一条后台 timer 创建路径的配置，不能写成“浮引全部剪贴板更新延迟是 1.3 秒”，也不是运行时测得的延迟。 另有直接服务变化检查入口（后文），应用状态是否会选择其他调用路径尚未完整覆盖。

Windows 设计建议：采用系统变化通知触发捕获，将兜底检测单独配置；后台检测周期不能直接当作用户操作的响应目标。

4. 服务变化检查区分外部变化和内部写回标记

0x1001df154，205-change-check.pseudo.c:47–53：读取服务 pasteboard 的 changeCount，只有不同于 lastChangeCount 才进入处理分支。

  • :54–80：记录当前时间和 latestExternalPasteboardChangeCount，清空 latestInternalPasteboardChangeDate/Count 的可选值。
  • :81–91：调用代次重置函数 0x1001df48c，再携带当前 lastChangeCount 与 captureGeneration 进入 0x1001fc3a4。
  • 相同序号时本函数不进入捕获分支。

证据：ev_55a174cca6aac47c358546db2a6afac11cee51e103999827fe4d36c2abb524e0。

另一个入口 0x1001c90d4（206-capture-branch.pseudo.c:60–140）在序号相同时，会比较可选的 latestExternalPasteboardChangeCount 与当前序号，存在日期时计算 timeIntervalSince 并与传入 double 比较后返回布尔值；序号变化时也更新标记、重置代次、进入同一捕获函数。

证据：ev_f5cd43226454b5396333c20de0337fb30ddbd62ad44c18f9ada0748c769bb592。

限制：后一函数传入的时间阈值来自调用者，本轮没有恢复该调用语义，不能猜为某种固定“复制等待时间”。字段的命名和赋值支持“区分内外部变化标记”，但完整自写回抑制规则仍需结合内部写入入口。

5. 用递增代次与取消任务处理连续复制

0x1001df48c，210-change-generation-reset.pseudo.c:11–30：

  1. 将 captureGeneration 加 1。
  2. 如果 captureRetryTask 不为空，调用 Swift.Task.cancel。
  3. 清空该任务字段并释放旧引用。

证据：ev_c76e81312937bd12b78b60c0d3b97a9cf7e8642fbcdca8d9cb841dee5b4aa3a7。

这是实际代码分支，支持“新变化使旧捕获重试失效”的结论。取消本身未必立即停止已运行的异步体，因此后面的序号/代次验证很重要。

Windows 可借鉴：每次剪贴板变化递增版本，用取消令牌取消旧任务，同时在提交结果前再次核对版本，避免旧结果覆盖新复制的内容。

6. 内容读取前后均有竞态检查，并有有界重试

0x1001fc3a4：

  • 209-capture-pipeline.pseudo.c:192–207：存在普通路径，要求输入序号仍等于当前 changeCount、输入代次仍等于服务 captureGeneration，不一致直接返回。另有低字节标志等于 1 的特殊分支，不替它猜业务含义。
  • :229–231：在 Objective-C autorelease pool 内调用 payload 读取函数 0x100205a44。
  • :233–242：检查可选 payload 是否存在；取得 payload 后再次读取 changeCount，只有仍等于读取前序号才继续构造后续路径与异步处理任务。
  • :390–405：构造后续异步任务；空结果或读取期间内容变化的路径进入 0x1002050f8。此处“序号没有变化”不是内容去重，不能写成已经恢复去重算法。

证据：ev_dfee34d4b472dc63a54b6706b6b6fad20b47bd32c6fd3014d06cc36ce9524c88。

0x1002050f8，207-capture-generation.pseudo.c:51–75：

  • 一个传入标志等于 1 时直接退出（语义尚未确定）。
  • retryIndex < 3 才允许继续，并要求当前序号和代次仍一致。
  • 重试前取消旧的 captureRetryTask，捕获 retryIndex+1，使用服务弱引用创建新的 MainActor 任务（:77–157）。
  • 静态切片 0x1020fe190/198/1a0 三个 64 位值为 200、600、1200，由此函数按重试索引读取。这个原始表值读取是补充二进制证据；异步等待 continuation 未展开，不将其单位猜作毫秒，也不宣称已确认退避时长。

证据：ev_081ad86716a6b4eb1dbef29fc7b3eac4da9e4d9f479ecfb1a622789f644b048f。

Windows 可借鉴：对暂时读不到剪贴板内容的情况设置有界重试；每次重试前校验内容版本，避免反复读取已过期的剪贴板。重试间隔需要 Windows 实测制定。

7. payload 识别有明确优先顺序，文本会裁去两端空白

0x100205a44，212-read-payload.pseudo.c：

  1. :40–62：先调用未展开的 helper 0x1001be780。结果存在时根据数组长度形成一个枚举分支；语义尚未确定，不能叫它“隐私过滤”或“文件路径读取”。
  2. :64–72：读取 pasteboard types 并调用未展开的 0x1001c12a8，依据其返回的状态进入另一类型分支。
  3. :73–116：在该状态为空的分支中，以 NSImage 类调用 canReadObjectForClasses:options:、initWithPasteboard:；图片可读时构造对应 payload，还尝试读取附带字符串并做 whitespacesAndNewlines trimming。
  4. :119–149：再尝试 NSPasteboardTypeString，桥接 Swift 字符串，裁去两端空白和换行，仅在 trim 后长度非 0 时返回文本 payload。否则返回空可选值。
  5. :158–181：前述 helper 状态非空时构造另一个枚举分支，具体类型需继续追 helper，当前不命名。

证据：ev_b8b24af5cf335eeb1b0443bc0be0013d4fb750486c1a383274ff2aa98d3a2796。

Ghidra 在 0x100205b78 明确报告无法恢复 jumptable，并将间接跳转当调用；本页只描述可读分支和已识别系统 API，不声称枚举所有类型都完整恢复。

Windows 可借鉴：定义清晰的多格式优先级，避免同一剪贴板对象同时保存成若干重复卡片；是否裁去空白应由产品决定，建议保留原文并单独生成整理预览，避免用户复制的缩进丢失。这是 Windows 设计建议，不是浮引已确认行为。

开发方案可采用上述已确认的竞态和任务管理思路；不能据未追到的函数体，把某种去重、隐私或落库算法归给浮引。
